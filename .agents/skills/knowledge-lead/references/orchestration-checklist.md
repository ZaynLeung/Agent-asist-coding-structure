# 编排模式判定与执行清单

## 一、模式判定

| 条件 | 模式 | 理由 |
| --- | --- | --- |
| 改动 ≤2 个文件，或有严格先后依赖 | 单 agent | 并行的协调成本高于收益 |
| ≥2 个互不依赖的大块，写作用域不重叠 | 多智能体 | 每个块有独立验收命令，可并行 |
| ≥3 个同构子任务批量扇出（逐主题、逐批资料） | workflow | 扇出后统一汇总，避免逐个对话轮次 |

反例（不要用多智能体）：
- 多个单元要写同一个 `knowledge/index.md` 或同一个图数据文件。
- 任务本身是“先抽结构、再按结构写正文”，存在强依赖。
- 只是一次只读巡检，产出的是修复清单。

## 二、派发前检查

- [ ] 每个任务的 `write_scopes` 与其他任务零重叠。
- [ ] 每个任务都有一条能自己跑通的验收命令。
- [ ] 有依赖关系的任务用 `blocked_by` 串起来，不靠“后一个等等”。
- [ ] 结构层任务与内容层任务分开派发，不在一个任务里同时改标题和正文。
- [ ] 明确告诉执行者：不要动作用域外的文件，不要 `git commit`。

## 三、执行中复核

- 汇报三件套：改动路径、执行命令、输出摘要（缺一项就退回）。
- 抽查方式：自己 `git diff` 看越界改动，独立重跑验收命令。
- 失败处理：回滚该作用域、重派；不带着失败继续合并。

## 四、验收清单

- [ ] `node .agents/skills/knowledge-graph-db/scripts/graph.mjs validate` 通过。
- [ ] `stats` 的节点/边计数与预期一致，无异常孤儿节点。
- [ ] 内容层改动：`knowledge/index.md` 链接可达，条目符合 `knowledge/templates/knowledge-entry.md`。
- [ ] skill 改动：`validate-skill.mjs` 退出码 0、0 警告。
- [ ] `git status` 只出现计划内的文件。
- [ ] 汇报给用户：产物路径 + 命令 + 结果 + 遗留问题。
