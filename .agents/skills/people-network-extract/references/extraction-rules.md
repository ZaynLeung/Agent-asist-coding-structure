# 抽取细则

配合 `people-network-extract` 的 SKILL.md 使用。字段约束以 `docs/contracts/data-model.md` §5 为准，本文件只讲怎么判断。

## 1. 关系方向

规则：`source` 是主体（动作发出者 / 身份拥有者），`target` 是对象。

| 原文 | 方向 | relation | category |
| --- | --- | --- | --- |
| A 是 B 的母亲 | A→B | 母亲 | 亲属 |
| B 是 A 的儿子 | A→B 或 B→A 都可，选主语侧 | 儿子/母亲 | 亲属 |
| A 被 B 保护 | B→A | 保护 | 合作 |
| A 保护 B | A→B | 保护 | 合作 |
| A 是 B 的上级 | A→B | 上级 | 同事 |
| A 是 B 的部下 | B→A（B 是上级）或 A→B「部下」 | 部下 | 同事 |
| A 与 B 是同事 | 任选主要一方，只录一条 | 同事 | 同事 |
| A 向 B 学习 | A→B | 学生 | 师生 |
| A 教 B | A→B | 老师 | 师生 |
| A 暗恋 B | A→B | 暗恋 | 恋人 |
| A 与 B 是对手 | 选主动方，只录一条 | 对手 | 敌对 |
| A 领导 B | A→B | 领导 | 同事 |

- 同一对人物可以有相反方向的两条关系（A→B「师父」、B→A「徒弟」），但只在语义确实需要时同时录。
- 对称关系（朋友/同事/同学/恋人）默认只录一条，避免库内重复与图上双箭头。
- 被动句先还原成主动句再定方向，这是最常见的错误来源。

## 2. 别名与同人判定

- 一个人只有一条 `persons`；`name` 是显示名，`aliases` 是归一化后能命中的其他写法：全名（"麦克·伊文斯"）、职务（"叶教授"）、绰号（"大史"）、外文名。
- 以下情况视为同一人：本名与姓名称呼、职务/头衔指代、明确的外号、同一人物在不同章节的不同译名（在 `notes` 标注）。
- 以下情况**不合并**：同名不同人（已知限制）、亲缘关系（父亲/儿子不是同一人）、称谓相同但指代不同的人。区分它们靠 `aliases` + `notes`。
- 不要把机构（ETO、科学边界）当人物；组织属于 `tags` 或 `notes`。
- `aliases` 不得与 `name` 重复，每项 ≤100 字符，数组去重。

## 3. 置信度

| 证据 | confidence |
| --- | --- |
| 原文明确直述"X 是 Y 的 Z" | 0.9–1.0 |
| 多处间接陈述可推出 | 0.75–0.9 |
| 单一暗示、语境推断 | 0.6–0.75 |
| 纯猜测 | 不要写进 relations，写进 notes |

同一关系被多份资料支持时，取较高值；重复入库时库内 confidence 取大、evidence 追加（见 data-model.md §4）。

## 4. 证据片段

- 直接从原文复制，不改写、不概括、不翻译；长度 ≤500 字符。
- 一句话含多条关系时，可让多条 `evidence` 共享同一句，但每条都要能独立读通。
- 证据必须能在资料里逐字搜到；做不到就说明这是推断，降 confidence 或改放 notes。
- `material.content` 建议保留全文；批处理时保留该批次原文（W001 是"未提供原文"警告）。

## 5. category 归类

| category | 覆盖关系举例 |
| --- | --- |
| 亲属 | 父母、子女、配偶、兄弟姐妹 |
| 朋友 | 朋友、同学、闺蜜、战友 |
| 同事 | 同事、上级、部下、领导、合作伙伴 |
| 师生 | 老师、学生、导师、徒弟 |
| 恋人 | 恋人、未婚夫/妻、暗恋对象、前任 |
| 敌对 | 对手、敌人、仇人、审判者/被审判者 |
| 合作 | 保护、帮助、邀请、追随、利用、雇佣 |
| 其他 | 无法归入以上、身份式称谓（引导、启示、继任） |

拿不准时用「其他」，不要发明新枚举；未知 category 会触发 W004 并被当作「其他」。

## 6. 未知、矛盾、缺失

- 资料没说的关系不补；缺失字段留空字符串，不要用"未知"占位。
- 两名来源冲突：保留证据更强的一条，`confidence` 取高值，把另一说法写进涉及人物的 `notes`（如"有资料称其养父为 X"）。
- 资料里的传闻/假设：可录但 confidence ≤0.6，并在 notes 标注来源性质。
- 人称代词（他/她/那个人）先找最近且语义通顺的先行词；指代不明时跳过该关系并在汇报里列为待澄清。

## 7. 批处理与合并

- 单批建议 ≤100 人、≤300 条关系；超过就按章节/主题拆文件。
- 每批一个完整 JSON，各自 validate；`material.title` 标批次（如"三体 第 1 章"）。
- 合并由 `people-network-db` 的重复 ingest 完成：人物按归一化名/别名合并，关系按 `(source, target, relation)` 去重。
- 合并前不要手工改 id；JSON 里没有 id 概念，人物只用名字/别名引用。

## 8. 好例 / 坏例

坏（方向反了）：

```json
{"source": "杨冬", "target": "叶文洁", "relation": "母亲", "evidence": "叶文洁是杨冬的母亲"}
```

好：`{"source": "叶文洁", "target": "杨冬", "relation": "母亲", "category": "亲属", "confidence": 0.95, "evidence": "叶文洁是杨冬的母亲"}`

坏（对称关系录两条 + 无证据）：`{"source": "汪淼", "target": "丁仪", "relation": "朋友"}` 与 `{"source": "丁仪", "target": "汪淼", "relation": "朋友"}`

好：只留 `{"source": "汪淼", "target": "丁仪", "relation": "朋友", "category": "朋友", "confidence": 0.85, "evidence": "汪淼与丁仪是朋友"}`
