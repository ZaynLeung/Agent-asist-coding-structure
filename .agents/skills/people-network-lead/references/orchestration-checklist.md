# 编排检查清单

`people-network-lead` 在派发前和收尾前各过一遍。任一"否"就停下来修计划，不要带着问题开工。

## A. 确认门禁检查（每次接到任务先过）

- [ ] 已做只读探索并读了 `docs/contracts/` 下相关契约。
- [ ] 已输出《执行计划确认单》，七项字段完整。
- [ ] 用户已明确确认（不是沉默、不是只问细节）。
- [ ] 确认前没有 spawn teammate、没有派发 shared task、没有写文件、没有改库。
- [ ] 需求变更后已重新确认。

## B. 模式选择

| 条件 | 模式 | 反例（不要这样选） |
| --- | --- | --- |
| 改动 ≤2 个文件且天然串行；或同一张表/同一个库必须顺序写 | 单 agent（Lead 自己做） | 为了"显得专业"硬拆成 3 个 agent |
| ≥2 个互不依赖的大块，各有独立写入目录，且总工作量超过一个人一轮能做完 | 多智能体 | 两人改同一文件；一个人做抽取一个人做入库但都写 `out/` |
| ≥3 个同构子任务（逐批抽资料、逐条核关系、批量改配色） | workflow | 只有 2 个任务就上 workflow |
| 需要外部资料/多角度研究后才能定方案 | 先只读研究（可 workflow），再按结果确认计划 | 一边研究一边改代码 |

## C. 派发前检查

- [ ] 每个任务只有一个可认领 owner；任务描述含输入、输出、验收命令。
- [ ] `write_scopes` 来自 `docs/contracts/ownership.md`，写到目录/文件级且两两不重叠。
- [ ] 依赖用 `blocked_by` 表达（如入库依赖抽取完成），不靠消息里口头约定。
- [ ] 需要共享的契约文件（`docs/contracts/**`）只读；要改先由 Lead 改并在确认单里说明。
- [ ] 数据库写操作串行；预览端口不重复（如 8765 / 8766）。
- [ ] teammate 的产出目录在任务里写死，避免都写 `out/` 或 `web/`。

## D. 收尾（Lead 必须亲自做）

- [ ] 收齐所有 teammate 的汇报：改动路径、执行命令、输出摘要。
- [ ] 逐一看 diff，确认没有越界写入、没有调试残留、没有 `git commit`。
- [ ] 亲自跑端到端验证（见 SKILL.md「验证」节），不以 teammate 的"已通过"替代。
- [ ] 契约对照：产出与 `docs/contracts/` 一致；有出入时以契约为准并在汇报里指出。
- [ ] 汇报用户：产物路径 + 验证命令与结果 + 遗留问题 + 建议下一步。
- [ ] 收尾后把 shared task 置 `complete`，失败任务先回滚再说明。

## E. 失败与回滚

| 症状 | 动作 |
| --- | --- |
| 任务改到作用域外 | 停任务 → 要求还原越界文件 → 必要时 `git checkout -- <path>`（只回退越界文件）→ 重派 |
| 两个任务冲突 | 停两者 → 重新切分写作用域 → 重发任务，不手工合并 |
| 验证失败 | 保留失败输出 → 定位是代码/数据/契约问题 → 最小修复后全量重跑 |
| teammate 卡住/超时 | 先 `list_agents` 确认状态 → `send_message` 问进度或 `interrupt_agent` → 必要时 Lead 接管 |
| 数据库被写坏 | 停写 → 用备份恢复 `data/people_network.db` → 重新 ingest → 重跑验证 |
| 确认单与实施不一致 | 停下来更新确认单并重新确认，不要自行扩大范围 |
