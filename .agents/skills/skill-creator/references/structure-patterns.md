# 结构模式与分层写法

先判断任务属于哪一类，再决定 SKILL.md 的骨架。四类覆盖绝大多数需求。

## 1. 流程型（procedure）

适用：步骤固定、顺序重要的任务（部署、发版、故障排查、文档评审）。

```text
SKILL.md
1. 前置检查（读什么、跑什么、缺什么就停）
2. 执行步骤（编号，一步一个动作，每步给出命令/工具与预期结果）
3. 失败处理（常见错误 → 判定 → 动作）
4. 验证（怎么算成功，跑什么命令/看什么输出）
scripts/     # 步骤里重复出现的确定性动作
references/  # 只有某一步需要的长清单
```

要点：每步都要有「完成信号」，否则模型无法判断是否继续；失败处理写「看到 X 就做 Y」，不要写「谨慎处理错误」。

## 2. 路由型（router）

适用：一个领域下有多条独立工作流，先进来再分流。

```text
SKILL.md
- 读取请求特征（文件类型、用户动词、目标产物）
- 判断条件 → 加载哪个子 skill（用 `skill` 工具按名加载）
- 平局时给用户的默认选择，并说明为什么
```

要点：正文不写具体步骤，只写判定条件和指向；绝不复制子 skill 的内容（否则改一处漏一处）。

## 3. 规范型（reference / format）

适用：输出必须严格符合某种格式或规范（报告模板、API 契约、命名规则）。

```text
SKILL.md
- 何时用、不何时用
- 输出契约：字段、顺序、单位、必填/可选、示例
- 校验方式：脚本或检查清单
assets/      # 模板、样例文件
references/  # 完整字段表、边界情况
```

要点：先用一个完整的正确样例立规矩，再列字段表；样例优先于散文。

## 4. 工具封装型（tool wrapper）

适用：围绕一个 CLI / API / 内部脚本的稳定用法（参数组合、坑、路径）。

```text
SKILL.md
- 环境与依赖：解释器、二进制绝对路径、缺失时的报错文案
- 常用调用：3~6 个可复制命令，标清输入输出
- 坑位：已知失败与规避
scripts/     # 包装脚本，负责参数校验与错误信息
```

要点：优先封装脚本而不是让模型拼长命令；脚本要幂等、失败给非零退出码和可读错误。

## 分层与长度

- SKILL.md 只放**每次都要用**的内容，目标 2~6 KB，硬上限 8192 字符（超过会被工具结果修剪器截断）。
- 长清单、完整字段表、大段示例放进 `references/`，正文用一句话指路：`需要完整字段表时读 references/fields.md`。
- 资源按需读取是常态：不为「完整性」把所有资料塞进正文。
- 每个资源文件都要在正文中被引用；没有入口的资源等于死文件。
- 引用一律相对路径（`references/x.md`、`scripts/y.mjs`），运行时按 skill 目录解析。

## 脚本设计

- 一个脚本做一件事；参数用位置参数或 `--flag`，`--help` 可读。
- 成功输出摘要（改了哪些文件、校验了什么），失败输出原因并以非零退出。
- 不写交互式提示（agent 无法应答）；不依赖当前工作目录，用绝对路径或 `import.meta.url` 定位。
- 不打印密钥；不把凭据写进文件。
- 无法确定依赖是否安装时，先检测并给出一句可执行的安装建议。

## 反模式

| 反模式 | 后果 |
| --- | --- |
| 正文写背景、动机、历史 | 占上下文，模型仍不知道做什么 |
| 一个 skill 塞多类任务 | 路由不准，加载后大半内容用不上 |
| 把子 skill 内容复制进 router | 两处维护，迟早不一致 |
| 只写「要小心/要专业」 | 不可执行，等于没写 |
| 所有细节都放正文 | 超过 8 KB 被截断，关键步骤丢失 |
| 资源文件写了但正文不提 | 永远不会被读取 |
